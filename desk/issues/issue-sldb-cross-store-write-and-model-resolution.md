# SLDB: support generic cross-store writes and federated model resolution

## Problem

SLDB has the beginning of a federated store model: a store index can link other stores through `stores:`, and global queries can include linked stores. That is enough for cross-store reading, but not enough for generic cross-store writing or model reuse.

Today, `docs create`, `docs track`, and related commands can operate on another store only when the caller passes an explicit store path. Model resolution is still tied to models registered in the destination store plus Python importability through `--pythonpath`.

That means a central store cannot yet act as a practical registry that lets a user stay in one project while writing a structured document into another project using a model owned by a third project.

## Desired Capability

SLDB should provide generic, workflow-agnostic cross-store document operations:

- Resolve linked store aliases from a central/current store, not only explicit `.sldb` paths.
- Resolve model references from linked stores, not only the destination store.
- Allow a document to be rendered/validated with a model owned by one store and written/tracked into another store.
- Keep the operation generic: documents, stores, models, paths, and payloads only.
- Avoid encoding desk-specific concepts such as inbox, request routing, sender, recipient, lifecycle, or assignment into SLDB commands.

## Example Shape

The exact CLI should be designed in implementation, but the capability should support a workflow shaped like:

```bash
sldb docs create \
  --store kgdb \
  --model deskops:InboxRequestDoc \
  -o desk/inbox/request-123.md \
  request.yaml
```

In that example, SLDB should treat `kgdb` as a linked destination store alias and `deskops:InboxRequestDoc` as a federated model reference. SLDB should not know that the path is an inbox request; it should only write and track a structured Markdown document.

## Deskops Usage Hint

`deskops` should own the workflow semantics and expose commands such as inbox/request routing on top of this generic SLDB layer.

For example, a future `deskops inbox send --to kgdb ...` should translate its workflow-specific payload into a generic SLDB document write:

- destination store: target project alias, such as `kgdb`
- model: canonical deskops inbox/request model
- output path: target project's inbox path
- payload: request fields generated by deskops

SLDB remains responsible for:

- resolving the target store;
- resolving the model;
- rendering Markdown;
- validating roundtrip/idempotency;
- writing the file;
- tracking or updating the destination store indexes.

Deskops remains responsible for:

- deciding what an inbox request means;
- sender/recipient semantics;
- routing policy;
- request lifecycle and status transitions;
- project/team/agent protocol.

## Implementation Notes

- Add a resolver that can distinguish explicit paths from linked store aliases.
- Consider model refs with a namespace form such as `store_alias:ModelName`, while preserving existing `module:Class` model refs where needed.
- Decide whether federated model resolution copies/registers a model into the destination store, references it remotely, or treats it as an operation-time model only.
- Keep write locking scoped to the destination store.
- Preserve current explicit `--store /path/to/.sldb` behavior.
- Avoid deskops-specific command names or fields in SLDB.

## Acceptance Criteria

- A central/current store can link at least two project stores by alias.
- A user can create or track a document in a linked destination store by alias without changing directories.
- A user can render/validate that document with a model resolved from a different linked store.
- Existing local-store `docs create/track/update` behavior still works.
- Global query behavior over linked stores is not regressed.
- Documentation explains how workflow tools such as `deskops` should wrap the generic cross-store operation without hardcoding workflow semantics into SLDB.
